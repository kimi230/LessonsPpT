# 00. 핵심 마인드셋 — AI를 제대로 쓰는 3가지 원칙

> AI 도구를 쓰기 전에 **반드시** 체화해야 할 사용자 측 원칙

---

## 원칙 1. LLM에게 멍청함을 들키지 마라

### 의미
- LLM은 **입력의 품질에 비례해서** 출력 품질이 결정된다
- 모호하고 두루뭉술한 질문 → 모호하고 두루뭉술한 답변
- 구체적이고 맥락이 풍부한 질문 → 정밀하고 실용적인 답변

### 실전 방법
- **역할·목적·제약·출력 형식**을 명시하라
  - Bad: "마케팅 전략 알려줘"
  - Good: "B2B SaaS, ARR $5M, 시리즈A, 엔터프라이즈 고객 타겟. 6개월 내 파이프라인 2배 목표. 채널별 ROI 기대치를 표로 정리해줘"
- **자기가 아는 것부터 먼저 제시**하라 — LLM은 빈 맥락에서 추측하지만, 맥락이 있으면 정교해진다
- "나는 이 분야 초보인데"라고 솔직히 밝혀도 좋다 — 단, **무엇을 모르는지를 구체적으로** 밝혀야 한다
- 질문 자체가 사고의 수준을 드러낸다 — **질문을 설계하는 능력 = AI 활용 능력**

### 왜 중요한가
- 01장(LLM 정의)에서 설명한 **"컨텍스트 의존성"** → 동일 모델이라도 프롬프트 품질에 따라 결과가 극적으로 달라짐
- 06장(컨텍스트 윈도우)에서 설명한 **"Lost in the Middle"** → 핵심 맥락이 잡음에 파묻히면 모델 성능 자체가 하락
- 11장(프롬프트 원칙)에서 정리한 GOLDEN 프레임워크의 출발점

## 원칙 2. 캡처 붙여넣기 질문을 습관화하라

### 의미
- 텍스트로 장황하게 설명하는 대신, **화면 캡처(스크린샷)를 직접 붙여넣기**하여 질문하라
- "백문이 불여일견" — LLM도 마찬가지. 시각 정보가 텍스트 설명보다 **정확하고 빠르다**

### 실전 방법
- **에러 메시지**: 터미널/브라우저 에러 화면을 캡처 → 붙여넣기 → "이 에러 해결해줘"
- **UI/디자인**: 현재 화면 캡처 → "이 레이아웃에서 헤더 부분만 수정하고 싶어"
- **데이터/차트**: 엑셀/대시보드 캡처 → "이 데이터의 이상치를 분석해줘"
- **문서/PDF**: 해당 페이지 캡처 → "이 계약 조항의 리스크를 분석해줘"
- **코드**: IDE 화면 캡처 → "이 부분에서 버그가 발생하는데 원인이 뭐야"

### 왜 중요한가
- 2025-2026년 주요 모델(GPT-4o, Claude 4, Gemini 2.5+)은 모두 **멀티모달** — 이미지를 텍스트만큼 자연스럽게 이해
- 캡처 한 장이 문맥 설명 10줄을 대체 → **컨텍스트 효율성 극대화**
- 텍스트로 설명하면 빠지는 세부사항(색상, 레이아웃, 정확한 에러 코드)이 캡처에는 **그대로 보존**
- "재현 환경을 그대로 보여주는" 가장 쉬운 방법

### 습관화 팁
- 단축키를 몸에 익혀라: `Win+Shift+S` (Windows), `Cmd+Shift+4` (Mac)
- 질문할 때 **"텍스트로 설명할까, 캡처로 보여줄까?"** → 후자가 가능하면 항상 후자

## 원칙 3. LLM은 지식의 샘이다 — 컨텍스트로 차원을 좁혀라

### 의미
- LLM은 방대한 지식을 가진 **깊은 샘(well)**이다
- 그러나 양동이(프롬프트)를 아무데나 내리면 **탁한 물**이 올라온다
- 우리가 해야 할 일: **특정 지식의 위치를 명확하게 차원을 좁혀주는 것**
- 그 역할을 하는 것이 바로 **컨텍스트**다

### 비유

```
지식의 샘 (LLM 파라미터 = 수조 개의 연결)
      │
      │  ← 양동이를 내리는 위치 = 컨텍스트
      │
      ▼
┌─────────────┐
│ 넓게 내리면   │ → 일반적이고 뻔한 답 (수면 근처의 탁한 물)
│ 좁게 내리면   │ → 정밀하고 깊은 답 (특정 지점의 맑은 물)
└─────────────┘
```

### 컨텍스트 낭비 = AI의 지적 수준을 낮추는 행위

| 잘못된 사용 | 결과 |
|-----------|------|
| 관련 없는 정보를 대량 투입 | "Lost in the Middle" → 핵심을 놓침 |
| 상충되는 지시를 동시에 제공 | 일관성 붕괴 → 모순된 답변 |
| 이전 대화의 잡음이 누적 | "Context Rot" → 대화가 길어질수록 품질 하락 |
| 질문 의도 없이 "아무거나 해봐" | 가장 확률 높은(= 가장 평범한) 토큰만 생성 |

### 올바른 차원 좁히기 방법

| 차원 | 예시 |
|------|------|
| **도메인** | "마케팅" → "B2B SaaS 마케팅" → "PLG 기반 SaaS의 엔터프라이즈 업셀 마케팅" |
| **역할** | "전문가" → "10년차 데이터 엔지니어로서" |
| **데이터** | 전체 보고서 → 관련 섹션만 발췌 또는 캡처 |
| **출력** | "알려줘" → "비교표로, 장단점 3개씩, 한국어로" |
| **제약** | "예산 1억 이내", "React + TypeScript만", "공개 데이터만" |

### 왜 중요한가
- 01장: LLM은 **확률 분포** 기반 → 컨텍스트가 분포의 피크를 결정
- 05장: RAG의 본질도 **관련 청크만 골라서 컨텍스트에 주입**하는 것
- 06장: 컨텍스트 윈도우는 유한하고, 채울수록 **주의력이 분산**됨
- 07장: 생산성 = 워크플로우 정의 + 모듈 조합 + **컨텍스트/데이터 품질**

---

## 세 줄 요약

1. **질문의 품질이 답변의 품질이다** — LLM에게 멍청함을 들키지 마라
2. **보여줄 수 있으면 보여줘라** — 캡처 붙여넣기가 텍스트 설명보다 낫다
3. **컨텍스트는 탄약이다, 낭비하지 마라** — 차원을 좁혀서 깊은 지식을 끌어올려라
